# WASM↔TS boundary benchmark — engine phase 1

> The commands below use the current paths; phase 1 ran them with `make engine-ts` and the `wasm-engine-release` preset.

Raw result: `boundary_phase1.json` (commit `e8b564c`, 2026-11-09). Generated by `engine/testing/bench/boundary.ts`:

```sh
WC="docker compose run --rm wasm"
$WC sh -c 'make ts && cmake --preset wasm-games-release && cmake --build --preset wasm-games-release -j'
$WC node engine/testing/dist/bench/boundary.js --module build/wasm-games-release/games/fixture_game.mjs \
  --out docs/benchmarks/bridge/boundary_phase1.json --commit $(git rev-parse --short HEAD)
```

## Environment

AMD Ryzen 5 5600GT (12 threads), WSL2/Docker, Emscripten 3.1.74 (Release, `ECS_ENABLE_ASSERTS=0`), node 20.18.0, V8 11.3.244.8-node.23.
Cache: L1d 32 KiB, L2 512 KiB, L3 16 MiB. Noisy environment: the ratios and the spread count, not the absolute numbers.

## Protocol

The same operation in the four variants, `position += velocity * deltaTime` (`deltaTime = fround(1/60)`), over N entities `Position {0, 0}` and
`Velocity {1, 2}` in a single archetype, one `World` per variant:

1. `cpp` — `fixtureMove(world, deltaTime)` (one call across the boundary);
2. `ts-engine` — `eachBlock` + `get`/`set` (normal use);
3. `ts-engine-raw` — `eachBlock` + `raw()` (separates the cost of the accessor from the cost of the stride);
4. `ts-manual` — four own `Float32Array`s, no engine (baseline).

Per N: 50 warm-up iterations per variant and 10 interleaved rounds (the order of the variants rotates every round); each measurement =
`ceil(4e6 / N)` iterations timed with `performance.now()`, in ns/entity. Median per variant; ratios over the medians. At the end,
each variant's `x` is checked against the f32 simulation of the accumulated value (relative tolerance 1e-3); a divergence aborts with exit 1.

## Reading

- The boundary itself is cheap: `eachBlock` crosses once per call, and the cost is in the loop. C++ in WASM runs at ~0.6–1.1 ns/entity;
  TS through views is 10–16× above that. That is the cost of keeping the game loop in TS.
- The `get`/`set` accessor is expensive: `ts-engine-raw` is ~1.4–1.8× faster than `ts-engine` (for example 4.6 vs 8.3 ns at N = 10000). With `raw()`
  the loop is within 1.1–1.45× of the manual `Float32Array` at N ≥ 10000, that is, the column-of-structs stride (AoS inside the component) costs little when
  the set does not fit in L1; what remains of the difference at N = 1M is the stride of 2 instead of 1 and the 24 B against 16 B per entity.
- At N = 1000 the ratios against `ts-manual` (8.9 and 6.4) are inflated by `ts-manual` itself (0.94 ns, loop entirely in L1 and vectorized by the JIT),
  while at N ≥ 10000 `ts-manual` jumps to ~4–5 ns, which was not investigated (suspicion: JIT behaviour/loop size, not the engine). That is why
  the ratio at N = 1000 should not be read as the cost of the stride.
- On the SoA-per-field decision (§4.2): the gain of having each field as a strided typed array is visible in `raw()` (close to manual) and disappears in the
  accessor with a method call per element. For hot loops in TS, the way is `raw()` or leaving the loop in C++; `get`/`set` serves
  less hot game code. There is no numeric target in this phase (§7).

## Loop cost — phase 2

Raw result: `loop_phase2.json` (commit `fca8946`, 2026-11-10). Generated by `engine/testing/bench/loop.ts`:

```sh
WC="docker compose run --rm wasm"
$WC sh -c 'make ts && cmake --preset wasm-games-release && cmake --build --preset wasm-games-release -j'
$WC node engine/testing/dist/bench/loop.js --module build/wasm-games-release/games/fixture_game.mjs \

```

Environment: the same as in the sections above (Docker on WSL2, node 20.18, V8 11.3, Release with asserts disabled). Protocol of `boundary.ts`:
warm-up, 10 rounds with the order of the variants rotating, median. One fixed step per `frame` (`frame(k / 60)`), no `Render` system.
No numeric target (§7).

|---:|---:|---:|---:|

### Boundary inside the loop (ns per entity)

| N | cpp-loop | ts-loop | ts-manual | ts-loop / ts-manual | ts-loop / cpp-loop |
|---:|---:|---:|---:|---:|---:|
| 1000 | 1.18 | 20.43 | 1.07 | 19.03 | 17.35 |
| 10000 | 0.80 | 11.20 | 5.69 | 1.97 | 14.05 |
| 100000 | 0.67 | 8.77 | 4.44 | 1.97 | 13.11 |
| 1000000 | 1.32 | 9.77 | 5.61 | 1.74 | 7.39 |

### Reading

- A callback into an empty TS system costs ~40–50 ns. A `frame` with no system costs ~90–110 ns; the engine loop itself is cheap.
- Interleaving costs no more than the number of calls explains: `alternating` and `grouped` tie (ratio ~1.0). It is not worth grouping TS systems because of the boundary cost; the order of the phases and of registration can follow the game's logic.
- A TS system with `eachBlock` and views, inside the loop, sits in the same range as `boundary.ts`'s `ts-engine` at N ≥ 10000 (8–11 ns/entity against ~8 ns). At ~2× `ts-manual` and 7–14× the C++ `move`, which repeats the phase 1 conclusion: the hot loop stays in C++.
- At N = 1000 `ts-loop` (20 ns/entity) is ~2× above `boundary.ts`'s `ts-engine` (~10 ns). Not investigated; suspects: `context.query(...)` on every step and JIT warm-up with 200 steps. Do not read the ratio at N = 1000 as the cost of the stride (`ts-manual` is also anomalous there, as in phase 1).

## Event cost — phase 3

Raw result: `events_phase3.json` (commit `3d331a8`, 2026-11-11). Generated by `engine/testing/bench/events.ts`:

```sh
WC="docker compose run --rm wasm"
$WC sh -c 'make ts && cmake --preset wasm-games-release && cmake --build --preset wasm-games-release -j'
$WC node engine/testing/dist/bench/events.js --module build/wasm-games-release/games/fixture_game.mjs   --out docs/benchmarks/bridge/events_phase3.json --commit $(git rev-parse --short HEAD)
```

Environment: the same as in the sections above (Docker on WSL2, node 20.18, V8 11.3, Release with asserts disabled). Protocol of `loop.ts`:
200 warm-up steps, 10 rounds with the order of the variants rotating, median, one fixed step per `frame`. Each sample runs
~1 000 000 events (`ceil(1e6 / N)` steps). N `Ping` events per step. The benchmark checks the sum of `value` read by the
handlers (N × steps) and exits with code 1 if it diverges. No numeric target (§7).

### Per-batch handler (ns per event)

Emission always through the native system `emitPings`. `none`: no handler; `cpp`: `addNativeHandler(Ping, "sumPing")`; `ts`: TS handler
that sums `value` through `batch.read()`. The last column is `(ts − cpp) × N`: the extra cost of the TS handler per batch, in ns per step.

| N | none | cpp | ts | ts / cpp | (ts − cpp) ns/batch |
|---:|---:|---:|---:|---:|---:|
| 16 | 21.74 | 22.96 | 35.52 | 1.55 | 201 |
| 256 | 15.00 | 16.20 | 19.76 | 1.22 | 911 |
| 4096 | 14.52 | 14.50 | 18.98 | 1.31 | 18333 |

### Emission (ns per event)

Both with `sumPing`. `cpp`: native `emitPings`; `ts`: TS system with N × `context.emit(Ping, { value: 1 })`.

| N | cpp | ts | ts / cpp |
|---:|---:|---:|---:|
| 16 | 21.34 | 169.70 | 7.95 |
| 256 | 14.23 | 170.49 | 11.98 |
| 4096 | 14.20 | 172.41 | 12.14 |

### Reading

- The callback of a TS handler costs ~150–200 ns per batch (N = 16: 201 ns, of which ~16 × 4 ns are reading). That is ~4× the
  call of an empty TS system from phase 2 (~40–50 ns): besides the crossing, each batch creates the `EventBatch`, does `sync()` and
  unlocks and locks the `World`. It is paid once per handler per round, not per event.
- Reading an event through the views costs ~4 ns per field read (N = 4096: (18.98 − 14.50) ≈ 4.5 ns/event). The TS handler stays at
  1.2–1.6× of C++ over the whole step, because emission and dispatch in C++ dominate.
- Emitting and dispatching in C++ costs ~14 ns/event with no handler. Not investigated (suspects: the queue's `resize` zeroes the bytes before the
  `memcpy`, and `emit` goes through `emitById` in another `.cpp`, without inlining); left for when a game shows the cost.
- Emitting from TS costs ~170 ns/event, ~155 ns more than in C++ (one crossing per event, plus validation and writing the
  value to the scratch area). With dozens of events per step that is a few µs; batched emission from TS is not worth it
  now. If a game emits hundreds per step from TS, emit from C++ or add batched emission.
